# Remaining limitations

1. The live database has no nullable columns in `shipment_assignments.completed_at` and `failure_reason`, even for an `ASSIGNED` task. New assignments therefore preserve the existing convention: `completed_at` carries the scheduled reference time and `failure_reason` records `No failure recorded`; no database migration was applied.
2. The live `delivery_otps` table requires `verified_at` and `consumed_at` to be non-null. The backend keeps the short-lived OTP challenge in process memory and writes the OTP row only after successful verification. A restart invalidates outstanding challenges; changing this requires an explicit database migration.
3. Existing imported customer/staff passwords remain unchanged. New customer registrations use PBKDF2; existing bcrypt hashes are supported when dependencies are installed, but no password reset was performed on imported accounts.
4. GPS sharing, rule-based delivery prediction, no-cost coordinate route optimization, Razorpay Test Mode integration, and optional SMTP email transport are implemented. The default transport remains in-app and SMS remains disabled because real SMS providers charge per message. Hosting is intentionally not included in this phase.
5. Financial screens are read-only summaries. Creating payments/refunds/COD settlements requires an accounts workflow and the live schema’s non-null actor/reference fields; no fabricated transaction is inserted.
6. Production hardening such as CSRF tokens, rate limiting, external secret management, HTTPS termination, backup/restore testing and observability are deployment work beyond this local academic deliverable.
7. The supplied staff records do not include a known plaintext password. Customer authentication and customer-to-staff authorization were live-tested; delivery-agent mutation flows are covered by the backend tests and implemented against the real assignment/OTP/proof schema, but were not executed by changing an existing staff credential.
